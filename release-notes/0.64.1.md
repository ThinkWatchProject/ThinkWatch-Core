This release lifts a 2 MiB limit on request bodies that the gateway never meant to have. A conversation holding a few inline screenshots passed 2 MiB and was refused from then on, compaction requests included, so the session could not be compacted back under the limit (#295).

**Upgrade notes**

- The control-plane protocol version (`CONTROL_API_VERSION`) stays at 40: ThinkWatch Lite 2026.10.7 connects to 0.64.1, and a server can be upgraded on its own.
- The request store's schema is unchanged: upgrading from 0.64.0 keeps the request history.
- The configuration format is unchanged.
- Message codes, compared with 0.64.0:
  - New: `gw.request.body_declared_too_large`, `gw.request.body_over_limit`, `gw.request.body_unreadable`.
  - Removed: `gw.request.body_too_large`, replaced by the first two: one for a declared length over the limit, which names the length the client declared, and one for a body found over the limit while reading, which has no size to name.

**Request size.** The gateway's only limit on a request body is now its own 256 MiB. The body used to be read by the web framework before the gateway saw the request, under the framework's default 2 MiB limit: anything larger got a plain-text `413 Failed to buffer the request body`, was not in the client's error format, and left no record.

The body is now read only after the source-address check, the key check and the POST check pass, so a connection that is not allowed in can no longer make the gateway hold its body in memory first. A request whose `Content-Length` is already over the limit is refused without reading the body. The limit is enforced on the bytes actually received, so a `Content-Length` that understates the body does not get around it. An oversized request is answered with 413 in the client's own error format (`request_too_large` for Anthropic clients), and `x-thinkwatch-error: request`.
