This release keeps outbound redaction away from the structure of a request, so a rule can no longer break the ids a client sends back, and lets a custom redaction rule look for its text as written or by a regular expression, with or without telling capital letters from small ones.

**Upgrade notes**

- The control-plane protocol version (`CONTROL_API_VERSION`) goes from 46 to 47. ThinkWatch Lite connects only to a core with the same protocol version: ThinkWatch Lite 2026.10.16 includes 0.70.1 (protocol 46) and does not connect to 0.71.0. A server used with it stays on 0.70.1 until the app is updated to a release that includes 0.71.0; `sudo twcore upgrade --version 0.70.1 --restart` switches a server back.
- The request store's schema is unchanged; nothing is cleared.
- Configuration: a custom redaction rule takes two new optional keys, `match` (`contains` or `regex`) and `case_sensitive`. **A custom redaction rule without `match` is now looked for as written and ignores case**; before, every custom redaction rule was a case-sensitive regular expression. A rule written as a regular expression needs `match: regex`, and `case_sensitive: true` to keep telling cases apart. Existing configurations load unchanged.
- New message codes: `config.rule_match_bad`, `security.redact_match_bad`.
- Changed in the protocol:
  - `CustomRuleSave` and `SecurityTestRequest`: `match` applies to redaction rules too (`contains` or `regex`; `contains` when not given); new `case_sensitive` (off when not given).
  - `Matcher`: `contains` and `regex` gain `case_sensitive`. A custom redaction rule is shown as `contains` or `regex`; tool-call rules, which are regular expressions that tell cases apart, report `true`.
  - `RuleSnapshot` gains `case_sensitive`; a custom redaction rule's snapshot now carries `matching`.

**Redaction leaves the request's structure alone.** Rules were run over the whole request body, field names and identifiers included, so a custom rule matched inside the ids a client sends with its history: Codex sends ids such as `fco_` followed by a hexadecimal UUID, and a rule whose text could be spelled in hexadecimal turned one into `fco_…<<TW_SECRET_1>>…`. The upstream rejected the request because the id contained characters an id cannot have, and since the history is sent again on every turn, every later turn of that conversation was rejected too. Rules now skip field names and the values of identifiers: `id` and any field ending in `_id` or `Id`, `type`, `role`, `name`, `namespace`, `model`, `status`, `object` and `phase`. What the client and the model wrote, tool arguments and tool results included, is searched as before.

**Private keys stay within one text.** The private-key rule looked for the end of a key block anywhere after its first line. A header without an end in one message, such as a file read halfway or code that spells the marker, joined up with an end line in a later message, and everything in between, earlier turns included, was replaced by a single placeholder. The header and the end are now looked for within the same text.

**Match by.** A custom redaction rule now says how it matches, as content rules already do: `contains` looks for the text exactly as written, so `.`, `*` and the like have no special meaning, and `regex` takes a regular expression. A rule matches regardless of case unless it sets `case_sensitive: true`. Code points remain a content-filter matcher only and are refused for redaction. The security log records how a custom redaction rule matched and whether it told cases apart when it found something.
