Core now adjusts execution capacity to traffic without requiring runtime settings. A small permanent I/O scheduler handles connections while CPU execution threads grow on demand and retire after ten idle seconds. Parsing, redaction, rewriting, decompression and plugins share CPU admission sized from available parallelism and memory, allowing a sufficiently provisioned 80-core server to run 80 CPU jobs concurrently. Concurrent small-body scans can expand too.

Release binaries use mimalloc to reduce allocation fragmentation and retained free pages. Linux builds disable transparent huge pages for the Core process where the kernel permits it, and Linux containers use their cgroup memory limits when sizing resources. Plugin sandbox threads retain their dedicated stacks and now start individually on demand and retire when idle.

Incoming bodies share a byte budget with headroom for parsing and copies. When that budget is occupied, new requests receive a retryable `429` with `Retry-After`. Reservations remain attached to buffered data until its final reference is released, and decompression reserves space as output grows. The 256 MiB per-request limit remains in place; the buffering budget is not a hard limit on total process RSS.

Existing configurations remain valid and no YAML changes are needed. CPU and memory ceilings are selected at startup; thread creation, admission and idle reclamation happen automatically during operation. Startup logs report the selected capacity, body budget, idle timeout and allocator. The control-plane protocol and request-store schema are unchanged.
