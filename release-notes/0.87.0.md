This release lets an upstream set a minimum generation speed: a streamed answer that keeps generating below it is ended with a retryable error, so the client sends the request again.

**Upgrade notes**

- The control-plane protocol version goes from 57 to 58.
- The request store's schema is unchanged (28); nothing is cleared.
- New configuration key `providers[].min_speed`; existing configurations are valid as they are.
- New message codes: `config.min_speed_range`, `gw.upstream.too_slow`.

**Minimum generation speed.** Some self-hosted servers occasionally drop to a few tokens per second partway through an answer and recover when the request is sent again. Neither the idle timeout nor failover covers this: content is still arriving, and it has already reached the client.

- `providers[].min_speed: { tokens_per_sec, window_secs }` turns it on for one upstream: `tokens_per_sec` from 1 to 1000, `window_secs` from 5 to 120 (20 when left out). Unset means off.
- From the first token on, a streamed answer (SSE or Bedrock eventstream) is judged once a second on its average speed over the last `window_secs` seconds, estimated the same way as the live speed.
- Pauses are not judged: nothing is decided while no content has arrived for over a second, and silences of 5 seconds or more (a quarter of the window when it is under 20 seconds) are taken out of the window and left to the idle timeout. Reasoning that arrives as a summary (Anthropic, Gemini, Bedrock, the Responses reasoning summary) is not judged either; raw reasoning such as Chat `reasoning_content` is. Judging stops once the answer has ended.
- Non-streamed answers, WebSocket turns and Gemini streams requested without `alt=sse` are not judged.
- Below the minimum, the answer ends with a 503 error in the client's format (Anthropic `overloaded_error`, Responses `server_error`, Gemini `UNAVAILABLE`) and the upstream connection is dropped. Claude Code and Codex resend the request on their own.
- The request fails with `gw.upstream.too_slow`, keeps the measured speed (also on `RequestFailed.tokens_per_sec`) and the usage generated so far. The upstream records one failure and the conversation stops sticking to it for that turn, so a resent request prefers another candidate. Upstream checkup and `/token-rate` medians leave out failed requests.
- `ProviderView` and `ProviderInput` carry `min_speed`; config packs, sharing and sync carry it with the upstream. One-click repair drops `min_speed` when the rate is out of range and resets `window_secs` to 20 when the window is.

**Gemini live speed.** The streamed output count no longer includes hidden reasoning (`thoughtsTokenCount`), which made the live speed read 0 until the text estimate caught up.
