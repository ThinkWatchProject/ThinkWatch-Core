This release lets a falsely matched value be excepted from outbound redaction without turning its rule off, adds per-rule hit counts for the security log, and stops rescanning conversation history that has not changed.

**Upgrade notes**

- The control-plane protocol version goes from 56 to 57.
- The request store's schema is unchanged (28); nothing is cleared. An index for the hit counts is added on first start.
- New configuration key `security.redact.exceptions`; existing configurations are valid as they are.
- New message codes: `config.redact_exception_duplicate`, `config.redact_exception_hash_bad`, `config.redact_exceptions_too_many`, `security.exception_forgotten`, `security.exception_not_exceptable`, `security.exception_saved_secret`, `security.exception_value_empty`, `security.exceptions_full`, `security.unknown_event`.

**Exceptions.** A value listed as an exception is neither replaced nor recorded by any redaction rule, in observe and replace mode alike. The rule keeps working for every other value.

- `security.redact.exceptions` holds up to 500 entries `{ sha256, masked, rule, added_at }`: the SHA-256 of the value (lowercase hex), the masked form shown when it was added, the rule that first recognised it, and when. The value itself is never written anywhere. The configuration manual notes that a hash of a short value such as a phone number can be guessed, the same way the file already holds upstream keys in plain text.
- Credentials saved in ThinkWatch (`thinkwatch-saved-secret`) cannot be excepted; such entries are ignored.
- `GET /security/exceptions`, `POST /security/exceptions` (a value, hashed at once), `POST /security/events/{id}/exception` (from a security-log row) and `DELETE /security/exceptions/{sha256}`. Adding a value that is already listed returns the existing entry; a full list answers 409.
- Adding from the log works for the latest 20,000 redaction rows while the core is running: their value hashes are kept in memory only, never in the request store, and are gone after a restart. Log views carry `exceptable` and `excepted` for those rows. A finding made of two overlapping matches is not exceptable, since no single value stands behind it.
- The trial marks an excepted value with `excepted` instead of reporting a hit.

**Hit counts per rule.** `GET /security/counts?guard=&since_ms=` returns `[{ rule, custom, count }]`, the sum of the log rows' counts for one guard since a time, from an index rather than by reading the log.

**History is not rescanned.** Clients send the whole conversation every turn. The gateway now keeps the redaction scan results of unchanged history (rule ids and positions only, never values) in memory, keyed by the rules in force, and scans only what is new. Results are identical to a full scan; rules that look at neighbouring text (field names, context words) bypass the cache. On a 200-turn chat, scanning a turn takes 0.25 to 0.46 of the time it took before, and a request is never slower than without the cache.
