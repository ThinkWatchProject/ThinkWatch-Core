This release lets core be replaced without closing the gateway port or cutting requests that are under way: the running core hands its listening sockets and its state to the core that replaces it.

**Upgrade notes**

- The control-plane protocol version goes from 51 to 52. The request store's schema is unchanged; nothing is cleared.
- No configuration key is added, renamed or removed.
- Upgrading to this release still restarts core the previous way. Upgrades from this release onward are seamless.

**Upgrades no longer drop requests.** A desktop app that is about to restart for an update now calls `POST /handover/arm`. Core stops following its parent process, opens a handover endpoint in the data directory, and waits for its successor.

- The successor finds the lock held by an armed core, connects, and takes over the control plane, the gateway listeners and the remote control port. The same kernel sockets are passed over, so connections that were queued but not yet accepted are served by the new core instead of being reset.
- The old core finishes the requests it already has (for up to 30 minutes) and exits. Responses WebSocket sessions are closed with code 1012 once their current turn ends, and clients reconnect to the new core.
- The new core starts from the old core's state: conversation affinity, circuit breaker and rate-limit pauses, latency and speed figures, load-balancing turns, OAuth access tokens, and key and upstream usage. While both cores run, slots and usage are settled between them, so concurrency and usage limits are not doubled.
- OAuth renewals are paused while the two cores overlap, because renewing a refresh token invalidates the previous one.
- Anything that fails before the new core commits leaves the old core serving. If the two cores speak different handover versions, the old core drains and exits and the new core starts as before.
- If the new version cannot read the configuration, it takes over only the control plane; the gateway keeps forwarding with the previous configuration and the takeover completes once the file is fixed.
- If no successor arrives within the wait, core reopens the desktop app once. If the app is still running, the handover is called off. Otherwise core drains and exits.
- `GET /status` reports `handover` (`idle`, `armed`, `taking_over` or `draining`) and `draining`, the number of requests the previous core is still finishing.
- New codes: `control.handover.busy`, `control.handover.endpoint_failed`, `control.handover.login_refused`, `control.handover.remote`, `control.handover.safe_mode`, `gw.oauth.held`.

**Dependencies.** `tokio` and `ctutils` are updated past RUSTSEC-2026-0386 and RUSTSEC-2026-0385.
